### Interview Prep Topics Covered

Three questions the interviewer asked in advance:
1. What is a component?
2. What shows repeatability?
3. What variants of a component do you see based on a wireframe?

**Scripted answer for "What is a component":**
> "A component is a self-contained, reusable piece of UI that owns its own markup, logic, and styling. It accepts inputs (props) and returns what to display. The key word is self-contained — if you can lift it out of the page and drop it somewhere else with different data and it still works, it's a component."

**Repeatability answer — grounded in the actual Ops Workbench screenshots:**
> The KPI tile appears 12+ times across the Overview screen. Every one is the same component rendered with different data. If it weren't a component, that UI would be copy-pasted 12 times — and changing the font size would require 12 edits.

**Variants identified (KPI tile):** currency, percentage, integer, ratio, duration, trend direction (red/green).

**Smart questions to ask the interviewer (architectural signal):**
1. "Is the KPI tile currently a shared component, or does each section have its own version?"
2. "Does the light/dark mode switch use CSS custom properties or a theme object passed through context?"
3. "The METRIC dropdown appears on every chart card — is that controlled or uncontrolled? Who owns the selected state?"
4. "When a chart is clicked and opens the work item drill-down, does that happen through routing or a modal?"

## 6. Ops Workbench Hierarchy and Routing

**Date:** ~2026-08-26

### Routing Structure
```
/app
 ├── /home                     Settlements Dashboard
 │    ├── /overview            default tab
 │    ├── /risk-view
 │    └── /work-view
 ├── /work-items               Work Items full page
 │    └── /:workItemId         split-panel detail (not a new page)
 └── /pst                      Priority Settlement Transactions
```

**Navigation mechanics:**
- Sidebar icons = top-level routing between three pages
- Tab navigation within each page = URL params or local state (not new routes)
- Work item detail = split panel slides in on row click — same URL, list context preserved

### Use Cases Per View
| View | Primary use case |
|------|-----------------|
| Overview | Morning situation check — scan KPIs for red arrows before starting work |
| Risk View | Root cause analysis — which fail reason is driving volume, are items aging past threshold? |
| Work View | Workload snapshot — queue size, assignment status, trend direction |
| Work Items | Task execution — claim, action, snooze, reassign individual items; bulk process repetitive tasks |
| PST | Investigation — full settlement transaction data, configurable columns, AI rule builder for prioritization |

### Detail: Work Items Components
- `<QuickFiltersSidebar>` — collapsible, Graph List vs. Fields List toggle
- `<FilterSection>` × 5 — Work Category, Work Type, Sub Type, Root Cause, Action
- Mini bar chart OR field dropdown per filter (same component, different render)
- `<BulkActionBar>` — appears on multi-select (Snooze, Reassign, Claim Work)
- `<WorkItemDetailPanel>` — split view, contains `<SnoozePanel>` with duration picker (15m / 30m / 1h / 4h / 24h / Specific date)

### Detail: PST Components
- `<ColumnGroupTabs>` — 8 column groups (Core / Depot/Custodian / Instrument / Client-Counterparty / Exceptions-Fails / Match Status / Narratives / Origin-Source Reference)
- `<ColumnVisibilityModal>` — show/hide columns per group with checkbox grid
- `<ConfigurePrioritizationModal>` — IF / ELSE IF rule builder
- `<AIRuleAssistant>` — natural language → prioritization rule (e.g., "Prioritize P1 items failing more than 5 calendar days in US or UK markets")

## 7. react-mentor-agent + react-task-board Evaluation

**Date:** ~2026-08-27
**Location evaluated:** `/Users/kilima.glenn/Sites/AI/react learning/`
**Projects found:** `react-mentor-agent/` (Node.js CLI) and `react-task-board/` (React 19 + TypeScript + Vite)

### react-mentor-agent — Assessment

**What it does:** CLI tool with commands (`learn`, `scaffold`, `challenge`, `submit`, `next`, `status`, `map`, `reset`). Adaptive level system (0–5), per-concept mastery (0–100%, threshold 80%), 3-tier explanations (eli5 / standard / deep), streak-based level adaptation, prerequisite enforcement, self-contained HTML preview generation.

**Strengths:**
- Prerequisite graph is correct — `lifting-state` requires `usestate + events-forms + children-composition`
- Scaffolder's `h()` helper mirrors React API in vanilla JS — previews work in any browser with no build
- Curriculum covers the right 12 concepts in the right order
- Each concept has predictions, misconceptions, and checklist check criteria

**Issues identified:**
1. No completion gate — solutions in `curriculum.json`, revealed after 2 failures. Self-reported pass/fail. Same AI over-reliance failure mode available via different interface.
2. Level oscillation at boundaries — 2 passes up / 2 misses down with no hysteresis. Learner at boundary bounces indefinitely.
3. TypeScript not tracked as a concept — mentioned in examples but not a learnable/submittable unit.
4. No connection to anchor project — `meta.anchorProject = "Dashboard + Task Board"` but `scaffold` generates new workspace files rather than pointing at `react-task-board/`.
5. No scaffold browser — no command to list existing generated previews.

### react-task-board — Assessment

**Tech stack:** React 19, TypeScript 5.6, Vite 6

**Strengths:**
- `Card.tsx` — correct generic container with `children: ReactNode` + optional `className`
- `KpiCard.tsx` — `type KpiCardProps = Kpi` reuses the shared interface; data type and component props cannot drift
- `Dashboard.tsx` — no hardcoded markup, pure `.map()` over data array. Data-driven pattern demonstrated clearly.
- `TaskBoard.tsx` — clean lifting-state: state owned by parent, children receive data down and callbacks up. `remaining` derived at render time, not stored in state.
- `AddTaskForm.tsx` — local draft state + `onAdd` callback is the exact lifting-state pattern.
- Comment quality is high — every file explains WHY the pattern exists.

**Issues identified:**
1. Typed event handlers not explicit — `e.target.value` and `e.key` inferred but not typed out. Missing the `React.ChangeEvent<HTMLInputElement>` syntax that will be asked in TS interviews.
2. No format variants on `KpiCard` — delta up/down variant exists, but currency/percentage/ratio format prop doesn't. This is the BofA KPI tile variant pattern.
3. No status/badge component — `PriorityBadge` (P1/P2) and `StatusChip` (Claimed/Available) are absent. Both are prominent in the Ops Workbench design.
4. `Card.tsx` renders `class="card "` with trailing space when className is empty (cosmetic, not worth fixing now).

**High-value 20-minute exercise before interview:**
Add a `format` prop to `KpiCard`:
```tsx
type Format = "number" | "currency" | "percent" | "ratio";
interface KpiCardProps extends Kpi { format?: Format; }
```
This gives a component with explicit TypeScript union variants built and owned by Kilima.

## 8. react-mentor vs react-sensei Comparison

**Date:** ~2026-08-27

Full comparison requested after evaluating both tools.

### Summary Table

| Dimension | react-mentor-agent | react-sensei |
|-----------|-------------------|--------------|
| Format | CLI commands | Claude Code conversation |
| Curriculum | Fixed 12 concepts, prerequisite graph | Open — any React/TS question |
| Sequencing | Enforced via prereqs | None — follows questions |
| Completion gate | None — solutions in curriculum.json | Hard gate — explicit unlock phrase required, every unlock logged |
| TypeScript | Mentioned in examples, not tracked | 3 tiers tracked separately from React level |
| Anti-gaming | Self-reported pass/fail | Canary threshold — 2 unlocks/concept across 3 sessions triggers intervention |
| Examples | Generates runnable HTML previews | Parallel example protocol — different domain, can't be reused directly |
| Your actual code | Cannot see it | Reviews pasted code, never rewrites |
| Anchor project | Designed around react-task-board (meta) | No anchor — works against any codebase |

### Recommended Usage Sequence

1. **react-mentor-agent first** — for sequenced fundamentals. `node src/mentor.js next` drives what to study. Scaffolded previews work in any browser.
2. **react-sensei for stuck moments** — when a concept isn't clicking after the mentor explains it, bring it into conversation. The dialogue mechanic handles the stuck moments.
3. **react-sensei for the actual job** — once in the BofA role reading real codebase code, the mentor's fixed curriculum is less useful. react-sensei works against patterns from any codebase pasted in.

### Critical Difference for Kilima's Profile

react-mentor-agent's completion gate doesn't exist — solutions are available after two failures or on request. For someone returning from AI over-reliance, that means the same shortcut is available via a different interface. react-sensei's gate is structural: requires explicit phrases, logs every unlock, intervenes on pattern.
